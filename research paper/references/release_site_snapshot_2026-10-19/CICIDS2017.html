1. FTP Patator

04-07-2017

The very first flow (with source port 52108) of the attacker connecting to the victim is actually a successful login (not brute force flow), likely executed by the dataset authors as a pre-test. No brute force occurs in this flow, so it shouldn't be labeled as such. Instead, we label it as an FTP Patator - Attempted flow.

The are also some flows that don't characterize the usual "Brute Force Behavior" (e.g. single failed login attempt, with timeout, after 5 minutes of inactivity). However, since a login attempt still occurs in these flows, we have opted to label them as malicious regardless.

Another interesting observation when we investigated this attack, was that for a handful of flows it looked like the flow is initiated by the victim. This appeared to be a simulation environment issue where somehow the SYN/ACK packet of the TCP connection had an earlier timestamp than the SYN packet. This issue was however rectified at the PCAP stage by running the 'pcapfix' and 'reordercap' tools as mentioned in the README of our GitHub repository.

3. DoS Hulk

05-07-2017

It looks like nearly the whole attack can be filtered/detected using just four conditions on Total Length of Bwd Packets (namely 11595, 23190, 11606 and 23201). Only 8 from 545,438 flows do not fall under this filtering. After inspecting these flows individually, those with Src ports 48678 and 43664 do not look to contain traffic that is part of the attack, and instead look like web-page browsing traffic. We assume the authors were surfing to the web-server manually mid-attack.

As mentioned in our previous paper on CICIDS 2017, this attack is mis-implemented. In short, this attack relies on a combination of HTTP header fields:
- Connection: Keep-Alive
- Cache-Control: no-cache
- Keep-Alive: X (with X representing a value in seconds, usually set higher than 110)
However, in all DoS Hulk traffic the "Connection" header field is set to "close", meaning that the victim will terminate the connection after sending the HTTP response (without waiting X seconds). Based on this, the entirety of this attack should strictly speaking be labelled as Attempted with category 5 - Attack Implemented Incorrectly. However, since this large volume of traffic still looks anomalous, we opted to keep the default label of DoS Hulk (no "Attempted")

5. DoS Slowloris

05-07-2017

The connection pool of the victim seems to get exhausted at around 12:49:12, and the first flow to stop responding is on port 54470. Ports 33358, 33360, 33362 look to be web page navigation on the app, not traffic related to the actual attack, possibly caused by the tool being shut down.

There was also a flow with Src Port 54114 that seemed like normal web navigation to the victim webserver.

The authors additionally performed an (accidental?) early launch of the tool between [2017-07-05 12:48:46.211817] and [2017-07-05 12:48:46.264300]. These flows have the attacker send the initial partial GET request, but then close the connection with a FIN packet after the server sends an ACK. Thus the attacker never starts sending the partial "X-a: b" HTTP headers that are characteristic of the attack in this dataset. These flows are thus labelled as "Attempted"

Other than that, this attack does manage to bring the websever down, so we see a lot of connection attempts that the webserver is simply unable to respond to. These will be labelled separately as "Attempted - Category 6, Target System Unresponsive".

10. Web Attack - Brute Force

06-07-2017

Under the labelling logic of the dataset authors, there are 151 total flows. There looks to be two clusters for flow types: - Total Fwd + Total Bwd Packets = 5 [72 flows]
- Total Fwd Packet = 204, Total Bwd Packets = 105 [69 flows]. These flows comprise of multiple login attempts.

Here too, in the beginning a couple of flows are simply the set up of the environment. For all of the web attacks, the authors use the Damn Vulnerable Web App (DVWA). For this attack, they did not use the dedicated Password Brute Force page as their target, but instead attacked the initial DVWA login screen.

What happens within one attack cycle is the following:
1. Initial POST request with a brute force login attempt
2. 302 redirect as HTTP response, which redirects to login.php, the normal login page, so we see another GET request which asks for dv/login.php, which prompts a normal HTTP response with the login webpage (the only difference being a message saying "login failed").
3. The user tries to go to /dv/vulnerabilities/xss_r/, but because he is not logged in he gets redirected back to dv/login.php again, which prompts another GET request to dv/login.php (we confirmed this behaviour using our own DVWA instance). We are not sure why this step was executed, as it seems obsolete. 4. The user launches another POST request with a brute force login attempt, restarting the cycle.

We also noticed a recurring pattern in the Brute Force flows. One seemingly normal GET request would be interlaced with a flow containing brute force attempts. Since these GET request flows do not contain any malicious traffic on their own, we have labelled these as "Attempted".

11. Infiltration

06-07-2017 and 07-07-2017

All communication between the attacker (205.174.165.73) and victim (192.168.10.8) seems to be a single TCP connection for infiltration traffic. The connection is initiated by the victim, after which the attacker issues commands which seem to be executed on the command line of the victim. The results of the executions are sent back to the attacker.

The first connection attempt initiated by the victim occurs at 17:19:02.547210, so it is assumed that the Dropbox exploit download occurred before this time. Interestingly, a few connection attempts from 192.168.10.9 are also made several minutes beforehand. 192.168.10.9 also visits Dropbox IPs beforehand, so it is possible that the authors performed a dry run. According to our findings, we think the Dropbox download exploit is a Meterpreter payload.

Just before and during the Infiltration attack, the victim does seem to be talking to several Dropbox ip's (162.125.4.6, 162.125.4.5, 162.125.3.1, 162.125.248.1) But the traffic is encrypted, so it's impossible to know which of these connections contain a malicious payload downloaded from Dropbox. (Wireshark filter we used: ip.addr eq 192.168.10.8 && frame contains "dropbox").

Since we cannot establish which Dropbox flow contains the malicious payload, we opted to keep the label for this traffic as Benign.

11.1 Cool disk - MAC

06-07-2017

This attack is completely missed in the original dataset's labelling. The main action happens between attacker (205.174.165.74 port 444) and victim (102.168.10.25 port 51325).
